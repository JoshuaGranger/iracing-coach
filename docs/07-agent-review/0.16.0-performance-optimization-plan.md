## 1. The dominant causes

### Observable A: ~20 s Progressive Tuning → Race Analysis

The chain is fully confirmed: `AnalyzeRaceAsync` discards the in-memory analysis Progressive Tuning is already holding (:896-897, no guard), falls to `TryLoadUiAnalysisCache` (:900), which misses because 25/29 entries are at dead schema versions, and falls through to a full backend re-analysis (:905-913).

The app records its own backend timings. Across all 29 runs: `total_ms` min 1,286 / **median 10,998** / max 23,855; `decode_analysis_ms` median 9,468 / max 20,721 — **86% of backend time at the median**.

**The arithmetic closes.** The owner's ~20 s sits between the median and large cases, and the backend's own self-reported 17.4–23.9 s on large races **nearly accounts for the entire observable by itself** — even if every C# term were zero. **No padding, and one honest caveat.** Only the backend terms are measured; the 4.4–6.3 s C# tail is estimated. It does not need to be right for the explanation to hold — it needs to be measured to size the fixes below it. See §4, item 3.

### The unifying defect

**Both cache layers have an observed hit rate of approximately zero.** 0/29 backend hits ever recorded; 25/29 UI entries dead; 19 orphaned pipeline generations. The 12–24 s analysis is not an occasional cold cost — **it is the steady state.** Every fix below that makes the miss path faster is worth less than the one fix that makes the cache hit.

## 2. The ranked fix list

Ordered by (user-visible improvement) / (effort × risk).

### Tier 0 — free or near-free

**1. Add the identity guard to `AnalyzeRaceAsync`.**
`CompanionState.cs:896-900`. Before nulling `CurrentRaceCard`/`CurrentAnalysis`, do what `SelectTuningRaceAsync:1237-1242` already does: if `CurrentAnalysis` already corresponds to this race, set `AnalysisWorkspaceOpen = true` and return.
*O(n) → O(1):* a full re-analysis becomes a pointer check.
*Improvement:* **~20 s → ~0** for the exact reported path. **Effort S, risk S.**
*Caveat, state it plainly:* this fixes Tuning → Analysis **on the same race**. Opening a *different* race still pays full cost. Do not let a tester open a different race, see 20 s, and conclude the plan failed.
*Verify:* log `CurrentAnalysis.TuningIdentity` vs the requested race at entry; assert zero `analyze_iracing_race` calls across the navigation.
*Risk control:* compare on strong identity (`EffectiveSelector` + the identity `ProgressiveTuningCoordinator.Matches` uses), never `race.Id` alone, or the workspace shows the previous race's telemetry — which is exactly what the comment at :1234-1235 exists to prevent.

**2. `WriteIndented = false`, hoisted to one static `JsonSerializerOptions`.**
`CompanionState.cs:3984` and `:3997`.
*Improvement:* 518 MB → ~265 MB across every cache read, write and the whole tray sweep. Also stops allocating fresh options per call, which defeats System.Text.Json's metadata cache. **Effort S, risk none.**
*Verify:* byte size of `data/ui-analysis-cache` after re-analysis; assert no `WriteIndented = true` on machine-read paths.

**3. Validate before parsing.**
`TryReadUiAnalysisCache:3510` and `TryLoadUiAnalysisCache:3379`. Read `schemaVersion` with a bounded `Utf8JsonReader` over the first ~256 bytes before touching the body.
*O(n) → O(1):* 407 MB of dead reads becomes 25 `stat` calls.
*Improvement:* removes ~3–5 s from every tray restore on its own. **Effort S, risk none.**

**4. Delete the duplicated read.**
`TryReadCachedRaceOverview:3479` re-calls `TryReadUiAnalysisCache` that the caller at :3642 just failed. Pass the known failure through.
*Improvement:* halves the dead-file cost on restore and in `EnrichRaceOverview`. **Effort XS, risk none.**

**5. Get the restore sweep off the dispatcher.**
`SetPrimaryUiVisible:2673` — raise `Changed` immediately, hand `QueueMissingHomeRaceAnalysis` to the thread pool.
*Improvement:* window appears instantly; the 6–10 s block becomes background work. **Effort S, risk S** (marshal `ApplySuccessfulRaceAnalysis`/`RaiseChanged` back — `ProcessHomeAnalysisRaceAsync:3706-3713` already demonstrates the pattern).
*Verify:* Dispatcher hang detector (§4, item 4).

**6. Delete the version-probe interpreter.**
`start-mcp.ps1:40-49`. Let `mcp_server.py` assert `sys.version_info` at import.
*Improvement:* −55–123 ms on **every** backend call. **Effort XS, risk XS** (preserve the discovery fallback at :19-34).

**7. Gate the background analysis queue on idle.**
`WaitForHomeAnalysisWindowAsync:3762-3775` — pause for user inactivity, not only `AnalysisLoading`/SDK-connected.
*Improvement:* stops the ~4.8-minute CPU storm from starting the instant you restore. **Effort S, risk S.**

### Tier 1 — structural, highest total leverage

**8. Summary sidecar (the caching layer).** *Files:* `CompanionState.cs` `SaveUiAnalysisCache:3930`, `TryReadUiAnalysisCache:3501`, `LoadArchivedRaces:3450`, `LoadArchivedSetups:3910`, `EnrichRaceOverview:3469`.
Write a few-hundred-byte `<key>.summary.json` alongside every cache entry holding exactly the fields `RuntimeMapper.Overview`/`ArchivedRace`/`ArchivedSetup` consume. Read only that on every catalog, restore and enrich path. Populate the empty `data/race-index` as the single-file catalog it was declared to be.
*O(n) → O(1):* catalog and restore become **O(races × ~1 KB)** instead of **O(total archive bytes)**. Per-refresh read drops from ~7.5 GB to a few MB; per-restore from 518 MB to <100 KB.
*Improvement:* the largest single structural win. **Effort M, risk M** (invalidate on `analysis.json` lastWriteUtc; keep the full parse as fallback on a sidecar miss).

**9. Make the cache able to hit.** *Files:* `CompanionState.cs:28-29`, `workflow.py:1523-1546`, `:1783-1799`.
(a) A `UiAnalysisCacheSchemaVersion` bump must migrate or evict, never orphan — 407 MB is orphaned today. (b) Narrow `pipeline_sha256` so formatting-only edits do not rotate it; **19 generations / 2.42 GB** is the measured cost of `inspect.getsource` over the full analyzer bundle.
*Improvement:* converts the 12–24 s analysis from a per-open cost into a genuine once-per-race cost. **This is the keystone — without it every other fix just makes a guaranteed miss faster. Effort M, risk M.**
*Risk control:* pair the narrowed hash with a test that fails when analyzer math changes without an explicit version bump (this is precisely the staleness the comment at `workflow.py:1524-1528` was written to prevent). Gate eviction behind the existing archive deletion policy.

**10. Persistent MCP session.** *File:* `McpBackendClient.cs:27, 82, 153-206, 249`.
Hoist `McpSession` into a field behind a `SemaphoreSlim`, handshake once, multiplex on the JSON-RPC id already generated at :211. Consider dropping the PowerShell hop entirely (`ProcessStartInfo` at :163-165 plus `PYTHONUTF8` already covers what the shim contributes).
*O(n) → O(1):* per-call process-tree creation becomes per-process.
*Improvement:* −1.4–1.8 s on every backend call; 5 process trees per refresh → 0. **Effort M/L, risk M.**
*Risk control:* per `AGENTS.md`, keep disposable workers for the long cancellable `analyze_iracing_race`; use the persistent session only for the short reads (health, dashboard, discovery, setups, garage61). Add liveness + restart on broken pipe; keep `entireProcessTree` kill for shutdown so the `App.xaml.cs:104` watchdog still guarantees no orphan.

**11. Stop shipping `lap_traces` in the response.** *Files:* `workflow.py:115-136` (`ANALYSIS_VIEW_FIELDS`), `mcp_server.py:1024`, `RuntimeMapper`, `TelemetryWorkspace.razor`.
**95.1% of `analysis_view` is `lap_traces`** (measured). It is already persisted to disk; serve it lazily when the workspace actually opens. Drop `indent=2` at `mcp_server.py:1024` regardless (measured 24.7 MB → 44.8 MB).
*Improvement:* 48 MB payload → ~1.2 MB. Removes most of the 3× C# parse, most of the RuntimeMapper cost, and most of the cache write. **Effort M/L, risk M** — this is a contract change: bump `ANALYSIS_VIEW_SCHEMA_VERSION`, regenerate `test-data/` fixtures, land the lazy loader **first** or the workspace renders empty.

### Tier 2 — large, real, lands after the above

**12. Python decode and engine constant factors.** Ranked here **not because it is small — it is the single largest term (9.5–20.7 s)** — but because items 8–9 remove it from the *repeated* path, and these are wide refactors. All are pure refactors:
- `ibt_reader.py:563-578` — precompute `struct.Struct` per variable, hoist the per-value re-resolution. **Measured 385 ns → 108 ns/value (3.6×)**; ~8.6 s → ~2.4 s at 22.4M calls.

- `analysis_engine.py` `TelemetryTable:371-481` — normalize each channel to float **once** instead of **20,352,144 `_finite` calls (509 per sample)**. Must still populate `accessed_channels:459-472` and must not sweep in `_bool`-consumed channels.
*Improvement:* plausibly 18–20 s → 6–9 s on a cold analysis. **Effort L, risk M.**

**13. Incremental archive integrity.** *File:* `DurableArchive.cs:187-191, 225, 327-351`.
Stop content-hashing 7.5 GB on `Initialize`. Verify on the `(path, length, lastWriteUtc)` triple already captured in `ArchiveComponentSummary`; hash only what changed; skip `telemetry-traces/raw/<sha256>/` entirely (the directory name **is** the digest). Reuse `Initialize`'s summaries in `PrepareForCopy` instead of recomputing at :225. Remove `EnsureRepository` from `SaveSettings:2300` and `DetectIRacing:2317`.
*O(n) → O(changed):* archive is append-only by design (class comment :107-110), so steady-state re-hash is near zero.
*Improvement:* removes a ~6–15 s **UI-thread freeze** on Save Settings/Detect, several seconds from cold start, and fixes the exit hang — `App.xaml.cs:99-106` force-terminates after 5 s while exit wants ~13.6 s of hashing, so the digest being computed is **never written**. **Effort M, risk M.**

### Tier 3 — real but minor; do only if free

Double first paint (`MeasureChart` invalidating all geometry — ~0.5 s, cheap, worth taking); `ShouldRender` + memoized `CapabilityContext` + page-gated `RaiseChanged` (idle CPU, not the 20 s); LiveTelemetry ring buffer and poll interval (background CPU); replay manifest O(n²) writes (real, not user-visible in either observable); `ServerGarbageCollection`/R2R — **explicitly second-order; re-evaluate only after allocation is fixed**, and measure idle working set, since Server GC allocates a heap per core in an app that lives in the tray.

### Refuted — do not spend effort, and do not restate as fact

- **WebView2/Blazor rebuild on tray restore.** `MainWindow.xaml.cs:42-53` constructs the DI graph, `BlazorWebView` and `CompanionState` exactly once; hide/restore is plain `Hide()`/`Show()` (:188-190, :124-128) and keeps the HWND and WebView2 alive. The entire tray cost is the one synchronous call at :123.
- **Debug builds / disabled hardware acceleration / cold dev WebView2 profile.** Both scripts publish `-c Release`; the only `AdditionalBrowserArguments` sit behind `if (!_hostProfile.IsIsolated) return;` and are network kill-switches, not GPU flags.
- **Event-handler leaks and eager logging.** All subscriptions balanced; every `DotNetObjectReference` disposed; the only `Trace`/`Debug.WriteLine` calls are on exit/uninstall paths.
- **O(n²) in `analyze_telemetry`.** Measured flat at 181/185/187/187 µs per sample across a 5.4× range. It is a linear pass with a large constant. Attack the constant, not an imaginary quadratic.
- **JS/chart interop as the 20 s.** Hard-bounded at 160 distance bins and 500 track points server-side, 1200 vertices client-side; one-shot payload 150 KB–1.1 MB, tens of milliseconds.
- **Telemetry ingest as the 20 s.** A 1–5% UI-thread tax. The layer's own auditor warned against letting "a multiplier of exactly the right shape" become the accepted explanation.
- **`Navigate()` itself.** `:2659-2671` maps a string, checks a capability, raises `Changed`. O(1).
- **Missing memoization in `TelemetryWorkspace`.** `MapTracePaths`, `ChartTracePaths` and `MetricRibbonSegments` **are** signature-keyed caches. The defect is that `MeasureChart` invalidates them once — not that they are absent.

## 3. Structural fixes vs point fixes

**Structural — each removes a whole class of waste:**

| # | Structural change | Class of waste removed |
|---|---|---|
| S1 | Summary sidecar + real `race-index` catalog (**item 8**) | Reading whole artifacts to answer summary questions |
| S2 | Cache identity that can actually hit (**item 9**) | Recomputation as the steady state |
| S3 | Persistent backend process (**item 10**) | Per-call process-tree creation |
| S4 | Payload contract — `lap_traces` out of the response (**item 11**) | Shipping presentation data to extract twenty scalars |

| S7 | Ring buffer for live history | Per-interval LOH copies of a bounded buffer |

**Point fixes that become unnecessary once the structural one lands:**

- **S1 subsumes:** merging the two archive scans; streaming `Utf8JsonReader` in both loaders; `EnrichRaceOverview`'s 6 × full parse; the duplicate read (item 4) and validate-before-parse (item 3) — *both still worth taking now as stopgaps, since S1 is Effort M and they are Effort XS/S.*
- **S2 subsumes:** loosening the ISO-8601 timestamp gate entirely — and note my correction: `sourceMatches` short-circuits **true** for archived races, so that gate is not the dominant miss reason and fixing it first buys nothing.

- **S6 subsumes:** the per-render interop guards (`ConfigureTrackMapInteropAsync`, `ConfigureContextSplitterInteropAsync`, `cursor.sync`).

**Sequencing.** Take Tier 0 first — items 1–7 are hours of work, remove both observables' *reported* symptoms, and carry near-zero risk. ## 4. Measurement plan

### What the existing probes actually do — and their blind spots

**`iRacingCoach.PerformanceProbe`** (`companion-app/tools/iRacingCoach.PerformanceProbe/Program.cs`): 100 warmup + 2,000 iterations of `JsonDocument.Parse(bytes)` + `RuntimeMapper.RaceCard`, reporting median/p95/max.
It is **blind to almost everything in this plan**, and by construction:
- it parses `bytes`, while production calls `JsonDocument.Parse(File.ReadAllText(path))` — so the UTF-8→UTF-16 decode and the LOH string are never counted;
- it maps `RaceCard` only, never `RuntimeMapper.Analysis` — the ~870k-dictionary-entry path;
- 2,000 iterations on one warm buffer means the file read, cold I/O, process launch and cache write are all outside the measurement.

**`iRacingCoach.CoachEngineProbe --prepare-local-archive`**: already calls `DurableArchiveService.Initialize(root, …)` then `PrepareForCopy(root, …)` against the real `Documents\iRacing Coach`. **This is already an exact harness for the double-hash cost** — it simply does not time it. Adding a `Stopwatch` is a two-line change that yields the archive number today.

### Regression guard

The guard that matters is **not** a wall-clock threshold — those are flaky and machine-dependent. It is an **assertion on bytes read**:

1. **Byte-budget test (primary).** Build a synthetic archive of N races. Run the catalog refresh and the tray-restore sweep through a counting `FileStream` factory. **Assert total bytes read per race is under a small constant, and that doubling N does not more than double it.** This makes the O(1)-per-race property structural rather than incidental, and it fails the instant anyone reintroduces a whole-archive read — which is exactly how this regressed into existence.
2. **Schema-migration test.** A bump to `UiAnalysisCacheSchemaVersion` must ship with a migration or eviction step; fail the build otherwise.
3. **Pipeline-hash test.** Fails when analyzer source changes without an explicit analysis-version bump — the guard that makes narrowing `pipeline_sha256` safe.
4. **No-indent assertion.** Fail if `WriteIndented = true` appears on a machine-read cache path.
5. **CI perf smoke.** PerformanceProbe p95 on a standard fixture with a generous threshold — a backstop for order-of-magnitude regressions, not a precision instrument.

**Bottom line.** Both observables are fully explained by confirmed, mostly self-recorded costs; neither requires padding. The 20 s is a cache that has never once hit (0/29) driving a 9.5–20.7 s Python decode on every open, plus a ~5 s C# tail. The tray restore is 518 MB of JSON — 75% of it provably dead — read and parsed twice on the UI thread before the window is drawn, followed by a ~5-minute background analysis storm. The cheapest fix in the plan (a six-line identity guard) removes the exact reported navigation; the most important (making the cache able to hit) converts the dominant cost from per-open to once-per-race.
