# Spike: Python backend as a Linux container worker

Date 2026-10-02. Read-only fact-finding. `S` = `iracing-coach/skills/analyze-iracing-race/scripts`. Line numbers are in the working tree at commit 8ce7170. "Inferred" = not directly observed.

## 0. Headline facts

- The backend already runs on Linux. In WSL Ubuntu (Python 3.12.3) the MCP server starts, answers `initialize`, lists 26 tools and serves `discover_iracing_sessions` and `garage61_auth_status` against empty roots (smoke run below).
- Unit tests under WSL: **1,347 run, 1,327 pass, 17 fail, 3 error, 10 skipped.** All 20 non-passes are Windows assumptions or test-environment (no real defect). Section 3.
- The real porting work is not path handling. It is: (a) Garage61 token loading is DPAPI-only, (b) every analysis copies the raw `.ibt` into `/data`, which conflicts with D4, (c) tool path bounds force recordings and setups to sit under one configured root, (d) float and hash determinism (section 5).
- The worker is `S/mcp_server.py` (stdio JSON-RPC lines). `S/coach_cli.py` covers only 17 commands and lacks compare, copy, structured tuning, trials, test day and reclaim. Use the MCP server.
- `IRACING_COACH_NETWORK_DISABLED` is set by the host (`companion-app/src/iRacingCoach.BackendClient/McpBackendClient.cs:202`) but **no Python file reads it** (`grep -rn NETWORK_DISABLED iracing-coach` returns nothing). Offline mode is enforced only by the caller.
- `vendor/` (PyYAML) does not exist in the repo. The Windows oracle runtime has no PyYAML, so session info is parsed by the in-house subset parser (`S/ibt_reader.py:400-520`). The container must not install PyYAML (section 1, row 17).

## 2. Worker interface for v1 (D8, D9)

### Transport and lifecycle (today)

- The host starts one process per call: PowerShell, then `python -X utf8 -u mcp_server.py`, sends `initialize`, `notifications/initialized`, `tools/call`, reads the reply, then kills the process tree (`McpBackendClient.cs:72-95, 241-255`).
- `S/mcp_server.py:1285-1298` is a serial stdin loop (one JSON-RPC object per line). A tool result is one `content[0].text` holding compact JSON (`:1272-1274`). A tool failure is in-band: `isError: true` with `{"error", "message", "tool"}` and a traceback on stderr (`:1275-1281`). Protocol errors use -32600, -32601, -32602, -32700. The server exits 0 on stdin EOF and never exits non-zero. Notifications (no `id`) get no reply (`:1244-1245`).
- `S/coach_cli.py:908-928`: success prints indented JSON and exits 0; any exception prints `{"error","message"}` to stderr and exits 1; `KeyboardInterrupt` exits 130; argparse usage errors exit 2. Secrets are redacted by key name (`:166-181`).
- Cancellation: none inside Python. No threads, signal handlers or multiprocessing anywhere in `S/` (grep). The host cancels by killing the process tree; deadlines are 30 s health, 2 min local read, 10 min `analyze_iracing_race` and `reclaim_report_storage`, 3 min `sync_garage61_references` (`McpBackendClient.cs:274-290`).
- Writes are temp file plus `os.replace` in the destination directory (`storage.py:668-681, 710-736`; `workflow.py:1990-1997`). A kill leaves `.write-*`, `.copy-*` or `.<name>.<pid>.tmp` orphans in `/data`. I found no cleanup code (inferred: not searched for exhaustively). SQLite WAL recovers by itself.
- Long-lived worker: feasible at the protocol level (the loop is already serial). Per-call start cost: importing `workflow` took 0.82 s cumulative under `-X importtime` in WSL (instrumented, so an upper bound; uninstrumented time not captured). Against it: `analyze_iracing_race` peaks at 2.1 to 2.3 GiB (round-2 snapshot) and Python does not promise to return that to the OS; `_automatic_gc_paused` (`workflow.py:2010-2030`) disables GC during a job; `ibt_reader._packed_struct` uses an unbounded `lru_cache` (`ibt_reader.py:631`); `setup_recordings.py:174-186` caches by `id(reader)`. Memory growth over many jobs: UNKNOWN, not measured. Matches AGENTS.md ("disposable backend workers for cancellable long jobs") and D2. Reasonable split (my recommendation, labelled as such): process per `analyze_iracing_race`; optionally one resident worker for the light read tools.
- `ArchiveStore.connect()` and many tools call `initialize()`, which creates nine directories and opens or creates `history.sqlite3` (`storage.py:1191-1204`). `call_tool` constructs an `ArchiveStore` for every tool except `compare_iracing_setups` (`mcp_server.py:941-949`). "Read-only" tools therefore need a writable `/data`.

The snapshot's own diagnosis of what remains: creating Python floats for decoded and converted columns, per-bin trace reductions, and JSON serialisation (round-1 snapshot line 116). Main-PC CPU model and N100 timings: UNKNOWN (no measurement on the mini PC).

Memory facts: `analysis.json` is 40 to 80 MB. Parsing a report costs "about ten times its size in memory" (comment at `S/storage.py:906-907`), so any tool that loads one (`_read_analysis`, `mcp_server.py:908-910`) can take 0.4 to 0.8 GB (inferred from that comment). The mini PC has 8.6 GB available and a full swap (owner brief): one analysis at a time with a memory limit above 3 GiB is the safe starting point (my inference).

### Natural order for a staged Rust port (recommendation)

1. **Fingerprint and IBT decode**: SHA-256 (`storage.py:582-587`, `2870-2880`), header and layout (`ibt_reader.py:829-1087`), session-info YAML subset parser (`:400-560`), column decode with sampling plan (`:1129-1167, 1211-1305`; `_strided_scalar_column` at `:225-272`). An oracle already exists: `tools/parity/emit_ibt_golden.py` emits the variable catalogue, sampling plan and a byte-level hash of the decoded value matrix "for C# parity testing" (its docstring); it can serve Rust unchanged.
2. **Column normalisation and per-sample kernels**: `_finite`, `_normalize_column`, `_fsum` means (`analysis_engine.py:205-337, 388-405`), then `_lap_summaries`, `_runs`, `_setup_channel_series`, `_setup_telemetry`, `_track_profile`, `_lap_trace_payload`, `_additional_trace_sources` (stage order in `tools/analysis_parity.py:100-126`; call order `analysis_engine.py:8676-8690`). These are the hot stages.
3. **Race foundations**: `build_track_geometry`, `build_race_replay`, `build_tire_learning` (`S/race_foundations.py`), groove analysis (`S/groove_analysis.py`), corner tire age.
4. **Decision and view layers**: `_strategy`, `_field_pace`, `_strategy_planning`, `_race_grades`, `_race_evidence_timeline`, `build_race_investigation` (`S/race_investigation.py`, `S/race_inspection.py`), race card and report rendering (`S/race_card.py`, `S/reporting.py`). These are pure functions of the analysis dict, so they can move last or stay Python longest.
5. **Persistence**: `_json_text` writer, report directory and history index (`storage.py`), analysis cache envelope (`workflow.py:2086-2200`).

### What `tools/analysis_parity.py` compares

- It imports the Python modules directly (`:65-66, 286`), so it cannot run a Rust implementation as is. It is the model for a file-level comparator.
- `capture` runs the production `analyze_race_workflow` on one `.ibt`, cold, in a fresh process and fresh harness-owned archive; one untimed run writes outputs, then `--runs N` timed runs (`:200-275`).
- Outputs byte-compared (`compare`, `:291-327`): the engine's in-memory result in insertion key order (`engine-output.insertion-order.json`); the cached analysis; `analysis.json` re-serialised with `indent=1`, sorted keys, `ensure_ascii=False`, `allow_nan=True` (`canonical_json`, `:175-182`); the workflow result; every persisted `.json`, `.jsonl`, `.md`, `.txt`, `.csv`, `.svg`, `.html` file; SQLite as a normalised row dump (`_sqlite_dump`, region of `:249-275`); a hash index of binary files.
- Normalisation, deliberately narrow (`:70-96, 138-172`): timestamp keys (`analyzed_at`, `created_at`, ... and any `*_at` holding an ISO instant) and report-directory timestamp slugs become `<timestamp>`; `analysis_sha256` of the cache envelope is replaced; `*_ms`, `elapsed_seconds` become `<elapsed-ms>`; the analyzer source digest is pinned to 64 zeros by monkeypatching `analyzer_bundle_sha256` (`:68, 286`).
- Everything else, "every lap, trace point, rounded float, catalog entry and channel list", must match byte for byte (docstring `:35-37`). The archive path must be identical between runs because paths appear in output (`:44-45`).
- Measured on four recordings (round-1 snapshot line 78): 203 MB NH race, 146 MB Iowa race, NH practice, NH test, all byte-identical.
- Not covered: tools other than analyze (setups, tuning, Garage61); `report.md`/`race-card.md` are covered only as persisted text; behaviour under a different Python version or platform; the SQLite file bytes (only the normalised rows).

## 5. Determinism hazards for a Rust port that must match exactly

| Hazard | Sites | What Python does | What Rust needs |
|---|---|---|---|
| `statistics.fmean` | 17 call sites, e.g. `S/analysis_engine.py:523, 1045-1046, 2367, 8128`; `S/reporting.py:1653-1654`; `S/test_day.py:581-582`; `S/race_inspection.py:229`; `S/investigation_study.py:79`. Bulk form `_fsum(numbers) / len(numbers)` (`analysis_engine.py:250, 388-405`). | `fsum(...) / n`; `math.fsum` is exactly rounded (Shewchuk). | An exact-rounding sum (a faithful `fsum` port). A plain `f64` loop or Kahan sum will differ in the last bit. |
| `statistics.pstdev` | `analysis_engine.py:7503, 8129` | Exact rational arithmetic (`Fraction`), then correctly rounded square root. | Exact-rational or double-double with a proof against the oracle; not `sqrt(mean(x^2)-mean(x)^2)`. |
| `statistics.mean` | `S/race_foundations.py:1159` | Exact `Fraction` mean converted to `float`; ints stay exact. | Same as above. |
| `statistics.median` | 54 call sites (grep) | For even n, `(a + b) / 2` on the two middle values after a sort. | Straightforward; must sort with total order and treat ints versus floats the same way (`median` of ints returns an int or half-int). Sort stability is irrelevant for values but NaN is not allowed in Python's sort result order guarantees; inputs are pre-filtered by `_finite`. |
| Builtin `sum()` | 173 sites (grep `sum(`) | **CPython 3.12 sums floats with Neumaier compensation**, not naive left-to-right. Container is 3.12; the oracle runtime is 3.12.14 (observed). Python 3.11 would give different last bits. | Port as compensated Neumaier in element order, or prove each site is on ints. Pin the container to 3.12.x. |
| `round(x, n)` | 370 in `analysis_engine.py` plus about 270 elsewhere (`grep -c "round("`); central helper `_round` at `analysis_engine.py:535-537`, copies at `groove_analysis.py:61`, `race_investigation.py:53` | Correctly rounded to the exact binary value, ties to even (dtoa mode 3). | Hash canonicalisation differs by site | `ensure_ascii` default True at `storage.py:463` (`stable_hash`), `evidence_records.py:143`, `artifact_identity.py:70`, `identity_contract.py:100`, `analysis_engine.py:1313`, `setup_catalog.py:968`, `workflow.py:1327`, `tuning_engine.py:874`; `False` at `analysis_engine.py:7995, 8005, 8294`, `race_foundations.py:147, 487`, `tuning_engine.py:847`, `storage.py:1106`, `workflow.py:1993`.
