# Versioned STO files

Owner request, 2026-10-23: browse/open/edit/save/save-as in Setups, preserve purchased originals, keep every saved version, validate in offline solo iRacing.

Imported `setup_files` occurrences are always locked, even when they are not purchased. They use version 1. ID `source:<sha256>` is SHA-256 of UTF-8 compact JSON `[customer_id,car_folder,relative_path,blob_sha256]`, in this order, no whitespace, Unicode unescaped, stored strings unnormalized. Lookups first scope rows to the driver. `coach:<positive file_id>` names a user-owned working lineage. StoFile.name contains the full relative_path for sources, distinguishing equal basenames in different folders. Native file values do not become observed garage/telemetry setup identity.

Save As forks the selected immutable `base_version`, applies edits, and creates version 1 under a safe unique .sto basename. Save requires If-Match equal to the working lineage's CURRENT version; its `base_version` may be older to restore history as a new version. Concurrent stale writes return 412; locked source Save returns 409. Nothing overwrites an existing revision or a source file. Exact duplicate name (Unicode lowercased key per driver/car), Windows reserved basename, path, control character and traversal names are rejected. Downloads add Coach identity and version to the filename; iRacing folder writes remain outside the collector.

Every successful write commits bytes, unchanged Python document, lineage pointer, an increment of user_data_generation, and a permanent idempotency receipt in one SQLite transaction. An Idempotency-Key is required. Receipt request SHA covers driver, source ID, action, parsed request JSON and If-Match. Reuse with changed content returns 422; identical retries replay the original result, even after a process restart. STO writes bypass generic request_log middleware replay so it cannot skip receipt validation. Receipts are retained with immutable history and are included in snapshots.

The small Python codec subprocess is serial, bounded to 16 MiB per source and 30 s, and kept inside the server's reserved memory; no analysis/light job is enqueued. This is an explicit exception to long Python-backed 202 jobs: no analysis or telemetry math runs. Source decode errors return StoDetail with document null and unavailable_reason; source download remains available. Generated versions retain Python document JSON and source bytes in SQLite, so old versions open when the codec material is temporarily unavailable; writes still require the pinned material. `/data/sto-profile.json` is private, never shipped or committed, and extracted from the verified offline simulator executable. Unsupported material fails closed. Runtime has no iRacing-utility dependency.

The editor shows native parameter units from Python. Geometry and enum names retain their native names unless car-specific garage mapping is established. It does not claim iRacing legality or setup effectiveness. Notes obey the native 0x4000-byte UTF-16LE bound including terminator. Unknown records, comments, unchanged decimal spelling, car identity and opaque trailing bytes are preserved. Server verifies generated SHA and exact bytes before committing.

`changes` is an exact native parameter name to raw decimal string map. Python rejects unknown or uneditable keys and invalid/nonfinite/range-invalid values; Rust and UI never convert native values or infer garage legality. Save As requires exactly one final .sto extension (case-insensitive); the server normalizes it to .sto, rejects repeated .sto suffixes, trailing dot/space, separators, control characters and reserved Windows basenames.

Changed numbers in either representation are serialized by Python as non-rounding fixed-decimal floating literals, with at least six fractional digits and bounded expansion. Numerically unchanged requests preserve the original token and container bytes. This is native syntax normalization, not value rounding or adjustment-grid clamping. The verified native writer uses `%f %s !` and its parameter loader accepts floating numeric tokens; an integer token can leave a garage parameter at its default. A client may still send an integer or exponent decimal string; Python emits an exactly equivalent floating literal or rejects an unrepresentable/oversized spelling. Native idempotency request hashes and already committed receipts retain their original meaning.

All imported occurrences remain visible even when their bytes equal an owned revision. Hash equality cannot distinguish a purchased source from its unchanged Save As copy.

## Verified garage representation (2026-10-23)

Native `StoField.raw_value`, `label` and `unit` retain their original meaning for older clients. An optional `garage` subtree supplies Python-authored label, display value, unit and editability. Optional min/max/step/step_base/choices describe only verified adjustment constraints. Each numeric quantity is a decimal string. A step requires its grid origin. Missing constraints mean unverified; an observed Tech failure or a tested interval is not a universal range. Display-only mappings without a proven inverse are not editable in garage mode. Garage labels and units are scoped by a content-versioned `garage_profile_id`, verified native identity and simulator build; a folder name or sampled value range cannot establish compatibility.

Dedicated `POST .../{file_id}/garage` and `POST .../{file_id}/garage/save-as` accept StoGarageWrite. These preserve the native routes unchanged and fail404 on an older server, avoiding silent loss of ignored optional garage edits. Python receives both maps, rejects overlap, validates the profile, converts garage edits, and checks verified constraints on changed fields in both maps. The legacy changes member is rejected on garage routes. Errors use422 with a stable code and optional native field name;412 remains the lineage If-Match conflict. Unchanged displayed numeric values preserve the original native token and bytes. No user input is silently clamped or rounded onto a grid. Float representation recovery requires proven native storage/format equivalence, rather than a generic tolerance.

Garage receipts include a distinct operation discriminator; existing native receipt hashes remain unchanged so previously unconfirmed native writes still replay. UI pending records retain the representation, exact endpoint, profile, body, If-Match and key. A mapping/profile change never silently reinterprets unsaved values.

Opening an owned revision may re-derive its descriptors with current Python code, preserving the selected bytes, hash, history and stored revision document. If current material is unavailable, native cached data remains readable but stale garage descriptors/profile are omitted. GET never advances a revision or user-data generation.
