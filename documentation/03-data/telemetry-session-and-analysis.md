# Telemetry, Sessions, and Analysis Data

This document defines the data behavior that underpins event discovery, analysis, live telemetry, planning, and tuning.

## Input discovery and lifecycle

| ID | Requirement |
| --- | --- |
| `TD-001` | The product MUST discover eligible local iRacing telemetry without requiring the user to copy a file into the app. |
| `TD-002` | A changing, zero-record, truncated, or trailing-partial IBT MUST NOT be advertised as a finalized event. |
| `TD-003` | Discovery MUST be repeatable and MUST avoid duplicate durable events for the same source identity. |
| `TD-004` | Split recordings and reconnects sharing a defensible session identity MUST group into one event while preserving source-part provenance. |
| `TD-005` | Qualifying and Race phases for the same event MUST remain separate analyses under one event context. |
| `TD-006` | Source files MUST be treated as read-only. |
| `TD-007` | Once an eligible IBT is finalized and accepted, the application MUST create an atomic, content-addressed durable copy under the Documents data home, verify its SHA-256 identity, and deduplicate identical content without modifying the original. The durable raw copy MUST survive restart, source-file deletion, migration, update, repair, and ordinary uninstall. It MUST NOT be pruned automatically; removal requires an explicit user-owned durable-data deletion action. |
| `TD-008` | A raw-copy failure MUST leave the original untouched, preserve any prior verified durable copy, and expose a bounded retryable state. An analysis whose raw copy is pending or failed MAY use the readable original, but it MUST record that future raw-channel reanalysis is not yet durable. |

## Normalization and analysis

| ID | Requirement |
| --- | --- |
| `TD-020` | Channel presence, units, sampling coverage, and validity MUST be recorded before calculations consume a channel. |
| `TD-021` | Lap validity MUST account for lap number, completeness, pit/service, incident, tow/repair, flag, and source-integrity evidence where available. |
| `TD-022` | Distance alignment MUST preserve lap-relative order and MUST not invent track geometry. |
| `TD-023` | Downsampling for display MUST preserve short extrema important to braking, throttle, RPM, steering, and acceleration interpretation. |
| `TD-024` | Run segmentation MUST use confirmed service or state transitions, not telemetry-file boundaries alone. |
| `TD-025` | Tire wear measurements at service MUST attach to the run that produced them; the final run remains unmeasured without a later observation. |
| `TD-026` | Fuel calculations MUST distinguish observed green/caution burn, inferred consumption, reserve, feasibility, and unsupported optimization. |
| `TD-027` | Damage analysis MUST keep incident, pit-road, stall, service, tow, mandatory repair, optional repair, and overlapping clocks distinct. |
| `TD-027A` | Incident-point events MUST retain their individual lap, point increment, recorded session time, before/after counter values, source-channel provenance, event type, and contact target only when each field is explicitly supplied. An explicit zero-point event MUST remain distinct from an absent event. Ordinary iRacing cumulative incident counters expose point increases but do not identify whether the cause was car contact, wall contact, off track, or loss of control. The UI MAY name one of those types or a contact target only from an explicit supported event field; it MUST otherwise show only concise recorded context such as point increase, lap position, session time, track-surface location, pit-road state, speed, yaw rate, or derived vehicle sideslip when each value exists. It MUST NOT show a placeholder type or source-method explanation. A displayed `x0` means an explicit recorded event added zero points and MUST NOT be interpreted as proof that no other zero-point contact occurred. |
| `TD-028` | Deterministic analysis MUST produce the same result for the same source, configuration, and engine version. |
| `TD-029` | Vehicle sideslip MAY be derived from recorded velocity components only when paired finite `VelocityX` and `VelocityY` samples exist, forward `VelocityX` is positive and usable, and planar speed is at least 5 m/s. The signed value MUST be `atan2(VelocityY, VelocityX)` converted to degrees; a failed guard MUST remain a gap. This derived vehicle-sideslip value MUST retain derived provenance and MUST NOT be described as a native `SlipAngle` channel, tire slip angle, or Yaw Rate. |
| `TD-030` | Every optional Race Analysis trace MUST have a stable identifier, human name, real unit, compact category, measured-or-derived evidence kind, source-channel provenance, and distance-aligned values. The catalog MUST contain only signals with usable values in the recording. Missing samples remain gaps; missing channels MUST NOT become zero. A derived tire, wheel, ABS, or condition signal requires an explicit defensible transform and MUST NOT borrow the value or name of a different physical quantity. |
| `TD-031` | Track geometry schema 1 MUST be keyed by exact track identity plus configuration/path and MUST record status, unavailable reasons, source hashes, coordinate system, main path, pit lane, pit-entry path, pit-exit path, start/finish, commitment line, and merge line independently. The cache MUST write atomically under `data/track-geometry` and MUST reject a record whose key, source identity, schema, or geometry validity does not match the selected configuration. |
| `TD-032` | Race replay schema 1 MUST preserve recorded participant identity fields and a bounded session-time frame stream from the first usable grid/parade state through available cooldown/post-checkered samples. Each frame MAY contain only supported car index, car number, class, driver/player identity, lap, lap distance, overall/class position, pit/track state, global session flags, and explicit per-car pace flags. The nominal 2 Hz field frame is a recorded-data sampling policy, not a claim that competitor telemetry exists between frames. |
| `TD-033` | Race replay MUST publish per-channel and per-participant coverage plus a stable unavailable reason. Interpolation MAY animate between two valid adjacent position samples for display, but it MUST retain the real sample timestamps, stop across gaps/state discontinuities, and MUST NOT create competitor control, fuel, tire, setup, incident, or lap-trace evidence. |
| `TD-034` | The replay event timeline MUST be derived from recorded flag/state transitions and explicit events. Duplicate samples MAY coalesce without losing start/end provenance; a missing event channel MUST remain unknown rather than becoming a clean or eventless race. |
| `TD-035` | The user's replay telemetry and fastest-clean overlay MUST use the same guarded, distance-aligned player trace contracts as ordinary Race Telemetry. ABS highlighting requires the player's explicit finite ABS-active samples and MUST retain gaps; it MUST not be derived solely from brake pressure, wheel behavior, or vehicle capability metadata. |

## Tire learning and capability model

| ID | Requirement |
| --- | --- |
| `TD-050` | Tire-learning schema 1 MUST store immutable, idempotent local observations under `data/tire-models`. Each observation MUST have a stable ID and identify NASCAR family, exact car, exact track configuration, setup scope, tire/compound when known, conditions, tire age, measured per-corner O/M/I endpoints, pace, controls, load, source analysis, and evidence coverage. Reprocessing the same source MUST not duplicate its contribution. |
| `TD-051` | The learned model MUST partition or explicitly weight evidence by compatibility. Exact car/track/configuration/setup/compound and materially relevant conditions MUST not be silently pooled with incompatible observations. The initial supported domain is NASCAR-first; other domains remain unavailable until independently validated. |
| `TD-052` | A model prediction MAY include remaining O/M/I wear, laps remaining, pace cost, and sustainable capability pace only when the matched local evidence meets a versioned minimum coverage threshold. Each output MUST include model version, evidence count/effective support, confidence, low/high bounds, matching scope, and exclusions. Insufficient, contradictory, stale, or out-of-domain evidence MUST produce null/unavailable output, not a wide but visually complete guess. |
| `TD-053` | The existing session-local calculated tire-wear trace is a stress-weighted allocation calibrated to measured run-end wear. It MUST remain separate from schema-1 learned observations and predictions: it has no independent O/M/I endpoint, historical capability, or confidence interval and MUST NOT train the model as though it were a measurement. |
| `TD-054` | Tire-model updates MUST be deterministic for the same ordered observation set and model version, use atomic replacement, preserve the last valid model after interruption, and remain portable with the Documents data home. Predictions MUST retain the exact model and observation-set fingerprint needed to explain or invalidate them. |
| `TD-055` | Garage61 representative-lap schema 1 MUST retain provider/scope, retrieval state/time, source-file hash, lap/setup identity, coverage, supported signals, and alignment fitness. External references MAY inform a separately identified comparison or capability prior only when authorized and compatible; they MUST never become local tire measurements or facts about an unobserved competitor. |

## Durable identities and cache behavior

| ID | Requirement |
| --- | --- |
| `TD-040` | Durable records MUST use stable identifiers sufficient to reopen the same event after app restart or relocation of the portable data folder. |
| `TD-041` | Cached analysis MUST record its source fingerprint, analysis version, configuration context, creation time, and invalidation reason. |
| `TD-042` | Reanalysis MUST be explicit when an existing result remains valid; invalid results MUST never be silently presented as current. |
| `TD-043` | User annotations and tuning feedback MUST reference durable event, phase, lap, setup, and recommendation identities where applicable. |
| `TD-044` | After discovery completes, finalized Race recordings without a valid current UI-analysis cache SHOULD enter one sequential background-analysis queue. Valid cached results MUST be reused across app starts, and the queue MUST deduplicate the same effective recording identity within a running process. |
| `TD-045` | Background cache generation MUST be lower priority than interactive use and MUST wait before starting another item while live telemetry is connected or an interactive analysis is active. It MUST NOT expose successful-job noise and MUST contain a failure to the affected recording. A failed or unsupported recording MUST remain explicitly retryable from Race Analysis. Cache entries MUST identify their schema, source identity or freshness evidence, and saved time so stale entries can be rejected. |
| `TD-046` | When Qualifying and Race share a SubSessionID, analysis MUST use the discovery `group_id` or an equally phase-qualified selector. Cache keys and cache validation MUST include both selector and phase; a response or cache for the sibling phase MUST be rejected rather than relabeled. |

## Live data boundary

Live telemetry is a separate transient path. It may update at driving cadence, but it must not mutate finalized history until a recording is complete and accepted by the ingestion pipeline. Display-rate movement between real samples does not create additional source samples and must not be persisted as telemetry. A fixture replay is test evidence for rendering and state transitions, not evidence that the iRacing SDK integration works on a real session.

## Current cache reality

Current source queues all discovered finalized Race sessions that lack a valid schema-10 UI cache whose stored selector, phase, and source-write timestamp match when the source still exists. Schema 7 first rejected pre-fix responses whose tire temperatures may have been converted without honoring the recorded source unit; later bumps through schema 10 also reject responses missing the exact-configuration map, replay, Technical data, tire-learning, authoritative geometry-hash, or tuning-identity fields now mapped by the coordinator. Discovery `group_id` is the primary selector; numeric SubSessionID remains a backward-compatible fallback. Interactive and background responses are checked against both the requested phase and, when available, the exact requested group selector before use. A sibling-phase or same-phase/different-event response is rejected rather than relabeled. The cache key contains the selector and phase, and cached response metadata is revalidated when read.

The deterministic workflow also qualifies its core analysis-cache identity and emitted `analysis_id` with the normalized selection identity: group ID, SubSessionID, simulator session number, and phase. Unknown legacy/file-only selections retain the base analysis ID rather than receiving invented session identity. The backend history index persists group, SubSessionID, simulator session number/type, and normalized phase. Reopening and history joins prefer exact group identity, then SubSessionID plus phase, then narrower legacy fallbacks; a Race result therefore cannot displace Qualifying merely because they share a SubSessionID.

The queue processes sequentially, persists successful responses under the portable archive's `ui-analysis-cache` component, and updates Home summaries without creating a visible success job. Live telemetry and foreground analysis pause the queue. A failed identity receives one quiet retry, then leaves the active set so a later refresh or app run can retry it instead of suppressing it for the remainder of the process. This is implementation reality, not proof that the source-write timestamp alone satisfies the stronger fingerprint/context contract in `TD-041` for every relocation or restoration scenario.

Deterministic backend archive/index/cache schema 2 adds the persisted session-identity fields and backfills legacy rows from their saved `analysis.json` when possible. SQLite initialization uses a 30-second busy timeout, retries transient locked/busy opens, enters `BEGIN IMMEDIATE` before the idempotent column/index/backfill migration, and rolls back on failure. This protects concurrent app/backend startup from racing the schema update; it does not turn a missing or ambiguous legacy identity into exact phase evidence.

Current analysis also emits a signed derived vehicle-sideslip trace from paired recorded `VelocityX`/`VelocityY` samples under the `TD-029` guards; Yaw Rate remains an independent channel. Focused Python tests passed 19 of 19, the coordinator mapper check passed 1 of 1, and one recorded Iowa IBT produced 542 valid derived samples plus 9 intentionally guarded gaps across four laps. That evidence validates the implemented derivation and gap behavior for the named recording; it is not proof of a native `SlipAngle` channel, tire-level slip, or representative correctness across every car and session.

Current coordinator mapping preserves individual nonnegative incident-point events, including an explicit zero when a source actually supplies one, instead of prematurely collapsing them into one lap total. Explicit event type and contact target, plus measured track location, pit-road state, speed, yaw rate, and defensibly derived vehicle sideslip, are retained only when the source supplied enough evidence. The Race Analysis rail may sum those events for its compact `xN` badge while retaining source-backed event rows for the tooltip. Current native iRacing counter-derived analysis still cannot discover a contact that produces no observable counter event or classify a counter increase as car contact, wall contact, off track, or loss of control; `x0` communicates an explicitly recorded zero-point event, not an exhaustive incident classification.

The current optional trace catalog maps only finite distance-aligned values present in the selected recording. Its supported families include controls, vehicle motion, per-wheel speed and derived spin/lock slip, tire pressure and temperature, fuel, chassis motion, conditions, and race state. Each available signal retains its stable identifier, actual unit, category, evidence kind, description, and source channels; for example, native fuel-use rate remains a mass rate in `kg/h` rather than being mislabeled as volume per hour. Missing channels and samples remain absent or gaps rather than becoming zero-valued traces.
